# Eyes Up — What is stored about students

**Date:** 4 November 2026 · **Code:** commit `0d0cfb0` · **Audience:** the owner, school leaders, parents' questions.

This document says, as exactly as the code allows, what Eyes Up keeps about a child, where it is, for how long, who can see it, and how it can be deleted. A short privacy statement a school could be shown is at the end.

## The one-paragraph answer

Eyes Up never asks a child for an account, email, surname, date of birth or login. A child types a **first name** (or taps it from a list the teacher made) and a room code. During the lesson the server keeps that name with every answer, drawing and photo the child sends, in memory. If the site is connected to its database (it is, on the live site), the same material is saved: **answers and names are kept indefinitely** in the lesson record; **photos and drawings are kept for 60 days** and then deleted automatically. Only the teacher who ran the lesson can open it afterwards. Share links the teacher creates hide individual answers but currently still include the list of first names who joined.

## Exactly what is collected

| What | Where it comes from | Example |
| --- | --- | --- |
| **First name** (up to 24 characters, whatever the child types) | Join screen, or tapped from the class list | "Ava", "Ben K" |
| **Class list** of first names | Typed by the teacher into Classes | "Ava, Ben, Chloe…" |
| **Class name** | Typed by the teacher | "Year 3 Blue" |
| **Every answer** the child sends | Each activity | poll choice, words, written text up to 3,000 characters, spellings, rankings, matches, table cells, tune notes, counter positions, calculator steps |
| **Drawings** | Sketch, Letter Formation, Annotate, Maths Board, Counters + Drawing | a PNG/JPEG of the pad |
| **Photos** (up to 6 per answer) and captions | Drop an Image, Image + Writing, Image + Long Answer | a 1,280 px JPEG from the child's camera or gallery, re-encoded on the device (metadata such as GPS location is removed by this step) |
| **Right / wrong marks** | Computed by the server, or set by the teacher afterwards | "✓", "3/5" |
| **Seat number and reconnection token** | Generated by the server | `s14`, kept on the child's device for 4 hours |
| **Technical:** the device's IP address appears in server logs only when a join is *refused* | Server log | "join refused: no_session code=ABCD ip=…" |

Not collected: surname (unless the child or teacher types one), email, date of birth, school, login, location, device identifiers, cookies for tracking. There are no analytics or advertising scripts; all code is served from the Eyes Up server itself (plus the optional Google/Microsoft/Canva slide player the teacher chooses to embed).

Two activities, **Ask a Question** and **Muddiest Point**, are anonymous: the server drops the name before the answer reaches even the teacher's own screen, and the stored record says `anonymous`.

## Where it lives

1. **In the child's browser.** First name (`localStorage`, until cleared), the current seat and room code (4 hours). Nothing else.
2. **In the teacher's browser.** The dashboard autosaves the last **10 lessons** (every name and answer, not pictures) to `localStorage` so a report can be recovered if the server restarts. This is **not** cleared by Sign out.
3. **In the server's memory** (Render, Frankfurt/Oregon/Singapore depending on how the service was created). The live room, all answers and all pictures, for **6 hours from when the room was created**, then dropped.
4. **In the Supabase Postgres database** (region chosen when the project was created). Tables:
   - `lessons`: one row per lesson: room code, title, teacher, when, and a JSON `summary` containing the roster of first names, the class name and list, and for every activity each named student's answer text and mark, plus any AI summary text. **Kept indefinitely.**
   - `lesson_images`: one row per picture: lesson, question, seat, **first name**, the image bytes, caption. **Deleted after 60 days** (setting `IMAGE_KEEP_DAYS`; cannot be set below 7).
   - `classes`: class name, the 5-letter sticker code and the list of first names. Kept until the teacher deletes the class.
   - `lesson_plans`: the teacher's own questions and option pictures. No student data.
   - `slide_decks` / `slide_images`: the teacher's slides. No student data.
   - `teachers`: teacher accounts (name, sign-in name, hashed password, optional email, plan, Stripe ids). No student data.
5. **Supabase backups.** On the Supabase **free** plan there are no automatic daily backups. On the Pro plan, daily backups are kept for 7 days. A backup contains whatever the database contained, so deleted rows persist in backups until the backup expires. (`CONTINUITY.md` covers this.)
6. **Render logs.** Refused joins include an IP address; retained for a short period (days) on the free plan. No names, answers or pictures.
7. **Anthropic (optional, only if the owner has set an API key and the teacher presses the button).** The written answer *texts* of a lesson, never names, are sent to Anthropic's API to produce a summary. Children may themselves type names into answers. Anthropic's API terms state inputs are not used to train models and are retained briefly for abuse monitoring; check their current data policy before enabling.
8. **Stripe (optional).** Teacher billing only; no student data.

## Who can see it

| Material | Live, during the lesson | Afterwards |
| --- | --- | --- |
| A child's own answer | The child (confirmation only), the teacher, and the classroom screen if revealed | The teacher who ran the lesson (reports, data page, spreadsheet) |
| Names on the classroom screen | Only when the teacher switches "Names" on; never for anonymous activities | n/a |
| Everyone's answers with names (spreadsheet) | The teacher; **and, today, anyone holding the room code** via the board's download token (see `SECURITY-REVIEW.md` §3) | The owning teacher only |
| Photos and drawings | The teacher; the classroom screen immediately on send unless "Hold answers" is on; **and anyone with the room code** (links are unauthenticated) | The owning teacher only, for 60 days |
| Share link (`/insights?share=…`) | n/a | Anyone with the link: aggregates and unnamed answers, **plus the roster of first names, class name and teacher name** (a gap to fix) |
| The database itself | The owner (Supabase dashboard) and anyone holding the database connection string | Same |
| Lessons with no owner (pre-account) | Every signed-in teacher | Every signed-in teacher |

The owner does not browse teachers' lessons from the admin page; the admin page shows counts only. The owner *can* open anything in Supabase directly.

## How long, in one table

| Material | Retention | Automatic? |
| --- | --- | --- |
| Live room in memory | 6 hours from creation | Yes |
| Answers and names in `lessons` | Indefinite | No deletion exists in the app |
| Photos and drawings in `lesson_images` | 60 days | Yes (`IMAGE_KEEP_DAYS`) |
| Class lists | Until the teacher deletes the class | Teacher-controlled |
| Share link | Indefinite | No revoke exists in the app |
| Teacher's browser autosave | Last 10 lessons, indefinitely | Overwritten as new lessons happen |
| Child's device | Name indefinitely; seat 4 hours | Clearing browser data |
| Server logs | Days | Yes (Render) |

## How a teacher or school gets data deleted

There is no "delete this lesson" or "delete this student" button yet (it is first on the fix list). Today the process is manual and goes through the owner:

1. The teacher (or school) emails the owner with: the teacher's sign-in name, the lesson date(s) or class name, and the child's first name if it is a single child.
2. The owner opens **Supabase → the project → Table Editor**.
   - To delete a whole lesson: open `lessons`, find the row (filter by `teacher_name` and `created_at`), note its `code` and `created_at`, delete the row; then open `lesson_images`, filter by `lesson_code` = that code, and delete those rows.
   - To remove one child from a lesson: open the `lessons` row, edit the `summary` JSON: remove the name from `roster` and `classRoster`, and remove that child's entries from every `items[].students` and `items[].noResponse`. Then delete that child's rows in `lesson_images` (filter by `student_name`). This is fiddly in the editor; the SQL Editor can do it, but have someone comfortable with JSON do it.
   - To remove a child from a class list: the teacher can do this themselves (Teach → Class → ✎ edit the names).
3. The owner asks the teacher to clear the dashboard autosave on any computer they used: in the browser, clear site data for the Eyes Up address (or, simpler, run ten more lessons; the autosave keeps only the last ten).
4. If the lesson was shared by link, the owner clears `share_key` on that lesson row so the link stops working.
5. If a Supabase backup exists (Pro plan only), the deleted data remains in backups for up to 7 days and then is gone.
6. The owner confirms completion in writing.

Aim to complete within 30 days of the request (common statutory expectation); in practice it is a 15-minute job.

## Related laws, in one line each (not legal advice)

- **Australia (Privacy Act 1988, APPs):** small businesses under $3M turnover are generally exempt, but schools you sell to are not, and they will ask for the statement below. Collect the minimum (first name only), tell people what you keep, keep it secure, delete it when no longer needed.
- **NSW / state public schools:** usually require vendors to complete a privacy/security questionnaire; this document and `SECURITY-REVIEW.md` are the answers.
- **If ever used in the EU/UK (GDPR / UK GDPR):** children's data needs a lawful basis (the school's public task), a data-processing agreement with each school, and a named way to exercise deletion. The deletion process above would need to be a button, not an email.
- **US (COPPA/FERPA):** FERPA treats the vendor as a "school official"; COPPA needs school consent for under-13s. Same practical requirements.

## Draft privacy statement for schools

> **Eyes Up — Privacy statement for schools (draft, [date])**
>
> **What Eyes Up is.** A classroom tool a teacher runs live on the board. Students join from any device with a 4-letter code and their first name. No student accounts, logins, emails or downloads.
>
> **What we collect from students.** The first name a student types or taps, and the answers, drawings and photos they choose to send during the lesson. Nothing else. Photos are shrunk on the student's own device before they are sent, which removes location and camera information. We do not use cookies for tracking, analytics scripts or advertising.
>
> **Why.** So the teacher can see who has answered, show responses on the classroom screen when they choose to, and look back at the lesson afterwards.
>
> **Who can see it.** The teacher who ran the lesson, and the classroom screen when the teacher reveals an answer (names appear on the screen only when the teacher switches them on; some activities are always anonymous). The Eyes Up owner can access the database for support and maintenance only. We never sell or share student data. If a teacher chooses to create a share link, that page shows class results without individual answers.
>
> **Where.** On servers run by Render (web hosting) and Supabase (database). [State the regions once confirmed in the Render and Supabase dashboards.] If a teacher uses the optional AI summary, the written answer text (never student names) is sent to Anthropic to be summarised.
>
> **How long.** Photos and drawings are deleted automatically after 60 days. Written and tapped answers, with first names, are kept with the lesson record so the teacher can refer back to them, until the teacher or school asks for them to be removed.
>
> **Deleting data.** A teacher or school can ask for any lesson, class list or individual student's data to be deleted by emailing [owner email]. We complete deletions within 30 days and confirm in writing.
>
> **Security.** Connections are encrypted (HTTPS). Teacher passwords are hashed. Student answers are only ever visible to the teacher who ran the lesson. We review the security of Eyes Up regularly and publish fixes promptly.
>
> **If something goes wrong.** If we become aware that student data has been accessed by someone who should not have seen it, we will tell the affected school within 72 hours of confirming it, say what was involved, and what we are doing about it.
>
> **Contact.** [owner name], [email]. Eyes Up is made by PeakYou, Australia.
